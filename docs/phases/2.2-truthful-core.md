# Phase 2.2 — Truthful Core

## Objective

Finish the current HotFox branch as a **truthful Android VPN core** before building new commercial/product layers.

Success is not “the APK builds”. Success is: the exact candidate APK routes real Android application traffic through the intended VPN path, survives lifecycle/network transitions, and never shows `Защищено` without evidence.

## Intended production path

`Apps -> VpnService/TUN -> HEV/tun2socks -> local SOCKS -> Xray -> VPN outbound -> server -> Internet`

The exact embedded Xray/libv2ray capabilities are authoritative. Never assume a socket `protect()` integration exists if the bundled library does not expose it.

## 1. Lifecycle ownership

Create one clear owner for each start/reload/stop operation.

Requirements:
- start generation/attempt cannot be completed by stale work;
- repeated starts during startup are idempotent;
- repeated stop does not create/supersede a new stop epoch while another stop owns teardown;
- low-level `coreController.stopLoop()` worker reports an outcome but does not independently publish session completion;
- owning teardown keeps barrier active until all cleanup is finished;
- late success after timeout belongs to the same stop operation and can safely finish cleanup/unblock restart;
- an old stop can never disconnect a newer attempt;
- exceptions in cleanup remain fail-safe and visible.

Cleanup inventory to reason about explicitly:
- pipeline jobs;
- traffic jobs;
- health jobs;
- network monitor;
- HEV/tun2socks;
- Xray core;
- TUN FD;
- browser dialer;
- receiver/callback registration;
- RootLanSharing;
- process network binding;
- notification/foreground state;
- canonical session state.

Deterministic tests should include:
- normal stop -> reconnect;
- stop timeout -> repeated stop -> late success -> reconnect;
- rapid connect/disconnect/connect;
- three stop requests;
- stale stop completion after newer attempt;
- exception during cleanup;
- destroy during connecting;
- destroy while connected;
- permission revoke while connected.

## 2. Xray shutdown callback generation safety

A temporal global Boolean is insufficient if delayed callbacks can arrive after handover.

Implement a generation-aware strategy. Acceptable patterns include:
- generation-aware runtime wrapper;
- expected-shutdown token associated with the stopped core generation;
- a conclusively drained old shutdown event before replacement generation is published.

Must distinguish:
- expected old-core shutdown;
- unexpected replacement-core shutdown;
- delayed old callback after replacement CONNECTED.

Tests:
- old callback during replacement readiness;
- old callback after successful handover;
- replacement dies while old shutdown is still expected;
- two rapid handovers.

## 3. Service/process reconciliation

Handle:
- Activity recreation while service alive;
- sticky service restart;
- process recreation;
- permission revoke;
- unexpected TUN loss;
- `onDestroy()` outside normal user disconnect.

On UI launch, reconcile canonical coordinator/service reality rather than rendering a stale persisted `isRunning` Boolean.

## 4. Path verification

Preserve component checks, but do not confuse them with end-to-end path truth.

Component evidence may include:
- TUN established;
- SOCKS5 handshake;
- HEV liveness;
- Xray running/egress.

Datapath evidence should correlate, within the same current generation and bounded window:
- traffic intentionally injected through Android VPN transport;
- actual response received;
- backend/forwarding progress observed;
- configured production path used.

Never mark connected from send-only traffic or independent component checks that could all pass while TUN forwarding is broken.

Useful structured report fields:
- attempt ID;
- backend;
- tunEstablished;
- socksReady;
- hevAlive/progress;
- tunForwarded;
- xrayEgress;
- DNS result when tested;
- duration;
- failure code;
- physicalDeviceE2e.

## 5. Loop prevention

Current fallback may bind the HotFox process to underlying physical network because the embedded library lacks desired per-socket protect behavior.

Audit carefully:
- outbound Xray must avoid tunneling into itself;
- verification traffic intended to prove TUN must explicitly traverse VPN;
- app control-plane traffic must have documented network selection.

Do not change to a new loop-prevention mechanism unless tests prove it works with the exact embedded core.

A later 3.0 option is a dedicated VPN engine process so process-wide binding has a smaller blast radius.

## 6. DNS / IPv6

For 2.2 release acceptance:
- DNS must not silently escape intended protection while `Защищено` is shown;
- IPv6 must be forwarded through protected path or intentionally fail closed according to policy;
- no implicit ISP fallback hidden by UI;
- network handover must not leave stale DNS/network bindings.

Physical testing should include dual-stack where available.

## 7. AUTO/server binding

Keep:
- AUTO row index 0;
- AUTO persisted independently from manual GUID;
- manual selection remains manual;
- resolved AUTO target is the exact config started by Xray;
- main UI shows resolved target truthfully.

2.2 does not require the full future health-scoring engine, but it must not choose a nonexistent/dead server and then claim success.

## 8. UI corrections required for current owner acceptance

The current 2.2 candidate should preserve/fix:
- three bottom destinations only;
- no primary side rail/drawer;
- route bars present and state-aware;
- no black-on-black icons;
- no square/missing placeholder elements;
- first screen not misleadingly empty;
- server list is contemporary editorial one-column UI;
- AUTO is first;
- subscription expiry shown when source supplies it;
- unknown status explains genuine absence/failure where practical;
- protected state only from canonical verified VPN session.

## 9. Artifact provenance

Mechanical builds happen in GitHub Actions.

Requirements:
- exact SHA in artifact/release notes;
- no older branch run may overwrite a newer shared mutable release;
- prefer one authoritative mutable publisher or immutable SHA/branch artifacts;
- emulator smoke is separately labeled non-E2E.

## 10. Physical acceptance

For the exact candidate SHA:

1. record external IPv4 before;
2. connect;
3. wait for canonical `CONNECTED`;
4. record external IPv4 after;
5. assert before != after;
6. verify after corresponds to expected server egress where metadata allows;
7. load real HTTPS browser pages;
8. verify another app uses network;
9. inspect DNS leak behavior;
10. inspect IPv6 behavior;
11. disconnect and confirm normal network restoration;
12. rapid reconnect;
13. Wi-Fi -> cellular;
14. cellular -> Wi-Fi;
15. screen off/wake;
16. permission revoke/service destruction sanity;
17. confirm real traffic counters progress.

Evidence must identify device, Android version, build SHA and resolved server without exposing subscription secrets.

## Exit gate

Phase 2.2 is complete only when:
- all applicable automated gates are green;
- trusted checkpoint review has no P0/P1 blockers;
- exact-sha APK exists;
- physical-device E2E is PASS;
- DNS/IPv6 policy has no release-blocking bypass;
- lifecycle/reconnect/handover are stable enough for release acceptance.
