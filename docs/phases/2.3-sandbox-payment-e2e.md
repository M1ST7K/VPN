# Phase 2.3 — Sandbox / test payment E2E

This document separates **what CI can prove** from the **manual provider-sandbox step** that still needs environment-injected credentials.

## Proven in automated tests

`SandboxPaymentE2e` plus `HotfoxCommercePaymentE2eTest` exercise:

1. authoritative backend plan catalog (prices/currency from the sandbox backend, not the APK);
2. idempotent order creation, including a lost create-order response that reuses the persisted idempotency key;
3. hosted-checkout handoff via `HostedCheckoutFixture` (open / browser return / cancel);
4. server-side webhook reconciliation: HMAC signature, duplicate event IDs, out-of-order PENDING after PAID;
5. entitlement issuance after a verified webhook, then retrieval/claim;
6. Keystore-backed credential persistence (`InMemorySecretStore` in JVM tests; `AndroidKeystoreSecretStore` on device);
7. authenticated sandbox manifest fetch and transactional sync;
8. AUTO remains selected and `VpnConnectHandoff` uses the existing 2.2 `HotfoxServerSelection.pick`;
9. that handoff does **not** start `VpnService` or publish `CONNECTED` / `pathVerified`;
10. restore after a simulated reinstall (empty secret store + recovery code / provider payment id).

Failure classes covered:

- duplicate webhook;
- out-of-order webhook;
- invalid webhook signature;
- lost create-order response;
- checkout cancel;
- app killed during checkout (persisted intent, new coordinator);
- payment while the app is offline (webhook applied, then relaunch poll);
- entitlement provisioning retry (`autoFulfill = false` then `completeFulfillment`);
- restore after reinstall;
- malformed/empty/unavailable manifest preserving last-known-good inventory and AUTO.

Browser `success=true` is never payment truth (`CheckoutReturnParser.isPaidProof` stays false).

## Not a production payment provider

The sandbox HMAC (`SandboxCommerceBackend.CI_WEBHOOK_HMAC`) is a **CI fixture**, not a YooKassa/Stripe/etc. private key. It must not be treated as a production secret.

`HttpHotfoxCommerceBackend` is used when `HOTFOX_PAYMENT_BACKEND_URL` is an `https://` origin. Provider private API secrets stay on that backend.

## Environment-injected real-provider sandbox (manual)

A hosted checkout against a real provider still requires credentials that this repo/CI does not contain.

To point a local/debug build at a real HotFox commercial backend:

```
HOTFOX_PAYMENT_BACKEND_URL=https://<hotfox-backend>
```

Optionally, for the in-app deterministic adapter (never a real card processor):

```
HOTFOX_SANDBOX_COMMERCE=true
```

Manual step still required for a live provider sandbox:

1. Configure the HotFox backend with the provider’s **sandbox** API keys (server-side only).
2. Install a debug APK built with `HOTFOX_PAYMENT_BACKEND_URL` set.
3. Choose a plan → complete hosted checkout in the provider sandbox.
4. Confirm the backend webhook moves the order to PAID/FULFILLED.
5. Confirm the app polls `getOrder`, claims entitlement, stores the credential, syncs servers, AUTO stays selected, then connect uses the 2.2 path.

Do **not** put those provider keys in the APK, git, or logs.
