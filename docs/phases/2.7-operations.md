# Phase 2.7 — Operations

## Objective

Make HotFox safe to distribute and operate for real users across dev/beta/stable channels.

## Release channels

Define explicit channels:
- Dev — fast engineering builds, not user release proof;
- Beta — candidate builds for wider testing;
- Stable — signed release with completed acceptance gates.

The channel should be visible in About/diagnostics.

Do not let arbitrary feature branches overwrite one shared mutable release.

## Artifact provenance

Every APK/release must identify:
- app version;
- exact git SHA;
- branch/channel;
- build type;
- embedded Xray/core version;
- build timestamp if useful.

Build info should be visible in About/diagnostics.

## Publishing model

Preferred:
- only one authoritative branch publishes mutable `Latest` per channel;
- feature/cursor branches keep Actions artifacts or immutable SHA-scoped prereleases;
- stale queued runs cannot replace newer releases;
- release tag/notes/APK point to the same SHA.

## Signed release automation

Stable pipeline should:
- receive keystore/password/alias through protected CI secrets/environment;
- never commit keystore or signing passwords;
- build signed APK;
- verify signature/certificate;
- produce SHA-256 checksum;
- preserve signing certificate continuity;
- upload exact artifacts;
- attach release notes/provenance.

Keep unsigned release compile as a normal engineering gate even before stable signing is configured.

## Update integrity

For sideload distribution, use an update manifest containing at minimum:
- schema version;
- channel;
- app version/versionCode;
- SHA/build identifier;
- APK URL;
- SHA-256;
- minimum supported updater version if needed;
- issued/expires timestamps;
- signature if a signed manifest model is adopted.

App must reject:
- checksum mismatch;
- invalid signature when signatures are required;
- accidental downgrade unless explicitly allowed in dev tooling;
- incompatible package/signing certificate.

No silent install.

## Supply chain

Generate/maintain where practical:
- SBOM/dependency inventory;
- license report;
- GPL/upstream notices/source obligations;
- dependency vulnerability scanning;
- secret scan;
- APK string scan for accidental private subscription URLs/tokens;
- signing/provenance verification.

Do not blindly auto-upgrade Xray/native dependencies just to satisfy a scanner; compatibility/security changes require explicit review.

## Diagnostics/support

Provide a safe support report with:
- app version/SHA/channel;
- Android/API/ABI;
- canonical session state/stage;
- backend type;
- selected AUTO/manual mode;
- resolved server display label;
- measured component/path status;
- DNS/IPv6 policy;
- latest sanitized error;
- last subscription sync;
- physical E2E evidence state where applicable.

Redact:
- raw subscription URL/token;
- VLESS UUID;
- passwords;
- auth headers;
- API/provider secrets;
- signing information that should remain private.

Add automated secret-corpus redaction tests.

## Crash reporting

Optional only after privacy design is approved.

If introduced:
- privacy-conscious/opt-in according to product policy;
- no raw configs/subscription URLs;
- sanitize exception breadcrumbs;
- user can understand/disable collection where required;
- release symbols/mapping uploaded securely if minification later exists.

Do not add invasive analytics SDKs by default.

## Privacy-safe operational metrics

If product analytics are ever introduced, minimize to aggregate operational events such as:
- app version/API/ABI;
- connection attempt success/failure category;
- server ID (not browsing destination);
- AUTO/manual mode;
- sanitized error code;
- purchase fulfillment state;
- subscription sync success/failure.

Do not collect browsing domain/DNS history for analytics.

## Backend operations

Commercial/control-plane backend should support:
- structured sanitized logs;
- request IDs;
- health checks;
- rate limits;
- webhook idempotency;
- payment/entitlement reconciliation;
- audit events;
- backup/restore;
- incident procedures;
- key/token rotation.

Reconciliation jobs should detect:
- paid order not fulfilled;
- duplicate/out-of-order provider events;
- refund not applied;
- entitlement/provider mismatch;
- stuck pending orders;
- manifest/provisioning failure.

## Status/incident mode

HotFox may expose a concise service incident banner from a trusted backend/status source.

Requirements:
- HTTPS/trusted data;
- expiration/freshness;
- no arbitrary remote HTML;
- no incident banner can change canonical VPN protection state;
- manual external subscriptions remain usable where independent.

## Remote config / feature flags

Optional after stable backend exists.

Requirements:
- versioned schema;
- issued/expires timestamps;
- signed payload if used for sensitive operational changes;
- allowlisted keys;
- last-known-good cache;
- safe local defaults;
- rollback;
- remote config cannot silently weaken core security invariants.

## Support/admin security

If an admin panel exists:
- separate authentication;
- least privilege;
- audit log;
- masked credential identifiers;
- no raw secret export by default;
- dangerous revoke/refund actions explicit/audited.

## Performance/battery operations

Monitor engineering metrics during soak tests:
- orphan threads/jobs;
- FD/resource growth;
- memory after repeated Activity/service recreation;
- health probe wakeups;
- route animation lifecycle;
- reconnect loop behavior;
- 30–120 minute session stability.

## Exit gate

A Stable release should be boring and traceable:

`reviewed source SHA -> deterministic CI gates -> physical acceptance -> signed APK -> signature/checksum/provenance -> stable channel publication`

with safe diagnostics/support and no hidden secret leakage.
