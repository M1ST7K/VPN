# Phase 2.5 — Privacy Controls

## Objective

Add useful privacy/routing controls without exposing raw Xray complexity to ordinary users and without creating bypasses that contradict `Защищено`.

## User routing modes

Keep normal UX simple:

1. **Smart** — deterministic HotFox defaults.
2. **All traffic through VPN**.
3. **Only selected apps**.
4. **All except selected apps**.
5. **Custom rules** — advanced.

Do not label deterministic rules as AI.

## Routing model

Use an explicit rule representation and tested precedence.

Rule targets may include:
- app/package;
- exact domain;
- domain suffix/wildcard with documented semantics;
- IPv4/IPv6 CIDR;
- local network ranges where applicable.

Actions:
- VPN;
- DIRECT;
- BLOCK.

Define conflict resolution once and test it. Do not let Android per-app rules and Xray domain rules contradict silently.

## Per-app routing

UX:
- searchable installed-app list;
- app name/icon/package secondary text where useful;
- clear mode: `Только выбранные` vs `Все кроме выбранных`;
- selection count;
- empty-state explanation.

Engineering:
- handle API 24+ VpnService allowed/disallowed semantics correctly;
- installed package removal/addition should not crash or poison settings;
- package inventory stays local by default;
- reconnect/recreate TUN safely when a rule change requires it.

## Domain rules

Advanced UX only.

Requirements:
- normalize case/trailing dot;
- IDN/punycode handling;
- validate wildcard semantics;
- reject malformed rules;
- deterministic precedence;
- DNS path must support the routing decision rather than leaking around it.

## CIDR rules

Support valid IPv4/IPv6 CIDR with strict parsing.

Never allow a malformed rule to accidentally become `0.0.0.0/0` or `::/0` DIRECT.

## DNS strategy

Default goal: DNS should travel through the protected path while protected.

Support a small understandable policy:
- `Автоматически через VPN` recommended;
- optional DoH provider;
- custom advanced resolver if needed.

Requirements:
- no silent ISP fallback while UI claims protected state;
- avoid bootstrap resolution loops;
- TLS validation for DoH;
- network handover refreshes stale resolver binding/state;
- behavior with Android Private DNS documented/tested.

## IPv6

Expose human policy, not cryptic toggles.

Possible product choices:
- `Защищать IPv6` when transport supports it;
- `Блокировать IPv6 вне VPN` when forwarding is not supported/desired.

Requirements:
- no silent bypass;
- dual-stack and IPv6-only/NAT64 environments tested where practical;
- route generation matches UI state.

## LAN access

Optional simple setting:

`Доступ к локальной сети`

When enabled, local printers/casting may bypass the VPN according to explicit route policy.

Test:
- RFC1918;
- link-local;
- IPv6 ULA/link-local as applicable;
- interaction with DNS and per-app routing.

Do not call LAN bypass secure/protected traffic.

## Kill switch / Always-on

The app cannot silently enable every protected Android system setting.

Provide accurate guidance to Android:
- Always-on VPN;
- `Block connections without VPN` where available.

Internal fail-closed behavior still matters for active HotFox sessions.

## Optional ad/tracker blocking

Only add after routing/DNS core is stable.

If implemented:
- maintained versioned domain lists;
- safe list updates;
- optional user allowlist;
- no fake `N threats blocked` counter;
- distinguish ad/tracker blocking from malware/antivirus claims;
- stale/missing list fails gracefully.

A future malware/phishing list must use trustworthy maintained data and must not be marketed as full antivirus.

## Smart mode

Smart mode should be deterministic and documented, for example:
- normal internet -> VPN;
- configured local/LAN -> DIRECT if user permits;
- explicit blocked domains -> BLOCK;
- explicit user exceptions override defaults according to documented precedence.

Do not silently downgrade a protected route because a domain is inconvenient.

## Routing change while connected

Define whether a change can be applied by core reload or requires TUN recreation.

Requirements:
- serialize with current session lifecycle;
- no overlapping old/new rules;
- UI indicates short reconnect when needed;
- on failure, do not keep `Защищено` with unknown rule state.

## Tests

At minimum:
- Smart/Global/Custom;
- per-app allow/bypass;
- deleted package;
- domain VPN/DIRECT/BLOCK;
- overlapping domain rules;
- IPv4/IPv6 CIDR;
- malformed rules;
- app + domain precedence;
- LAN enabled/disabled;
- DNS interaction;
- IPv6 interaction;
- rule change while connected;
- reconnect after rule change;
- process restart preserves intended rules.

## Exit gate

The user can select a simple routing/privacy mode and the generated Android/Xray behavior matches it deterministically, with no hidden DNS/IPv6 bypass while protection is claimed.
