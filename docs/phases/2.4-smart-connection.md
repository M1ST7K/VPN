# Phase 2.4 — Smart Connection

## Objective

Turn `Авто-выбор сервера` from a simple lowest-cached-ping choice into a real connection reliability engine.

Do not begin until 2.2 is physically verified and 2.3 commercial changes, if present, do not destabilize the VPN core.

## ServerHealthRepository

Introduce an explicit owner for server health state.

Per-server data may include:
- stable server ID/GUID;
- source/subscription ID;
- last probe timestamp;
- last success timestamp;
- last failure timestamp;
- latest latency;
- latency EWMA;
- jitter estimate;
- consecutive failures;
- availability: UNKNOWN / HEALTHY / DEGRADED / DEAD;
- probe source/type;
- optional trusted region/country metadata;
- optional real capacity/load only if control plane supplies fresh authoritative data.

Time-sensitive values must carry timestamps and freshness rules.

## Probe engine

Requirements:
- bounded concurrency, e.g. 4;
- per-probe timeout;
- global cycle timeout;
- stale job cancellation;
- battery-conscious scheduling;
- no aggressive continuous polling;
- exponential backoff for repeated failures;
- refresh on meaningful network/server events;
- no fake ping for untested servers.

If a server is not measured, display `—` / unknown, not `0 ms`.

## AUTO scoring

AUTO should consider a deterministic score based on available real data, such as:
- fresh latency;
- jitter;
- recent failure penalty;
- stale-data penalty;
- optional user region preference if explicitly configured;
- real capacity only when authoritative and fresh.

Do not market deterministic scoring as “AI”.

The exact scoring function must be unit-tested and understandable in diagnostics.

## Hysteresis

Avoid server flapping.

A candidate should not replace a healthy current server because it is only a few milliseconds faster.

Switch when:
- current target is unavailable/dead;
- health materially degrades;
- another candidate is significantly and sustainably better according to explicit thresholds;
- user explicitly requests reselect.

The UI should remain calm; AUTO target changes are not celebratory events.

## Failover

When AUTO current target fails:
- classify failure;
- choose next healthy candidate;
- use bounded retry count/window;
- apply backoff;
- update UI to `Переподключаем…`;
- preserve AUTO mode;
- show new resolved target after success;
- stop with actionable error if all candidates fail.

Manual selection must never silently fail over to another server unless the user explicitly chooses an option that permits it.

## Network handover

AUTO handover policy:
- keep current target when it remains healthy;
- re-evaluate when current target is stale/unhealthy or route materially changes;
- generation-safe lifecycle remains mandatory;
- health probes from old network cannot overwrite new-network results without freshness/generation checks.

## Server list UX

Preserve editorial one-column rows.

AUTO row remains first.

Manual row should show:
- city/server name;
- country/secondary label;
- real current/fresh latency;
- favorite;
- optional subtle availability state.

Health UI states:
- unknown: `—`;
- testing: subtle progress;
- healthy: `31 ms`;
- degraded: real value plus subtle warning if useful;
- dead: `Недоступен`.

Do not show a fake percent health score unless the underlying model genuinely supports and explains it.

## Live ping/test-all UX

Remove magic timing assumptions.

Testing should be event-driven:
- progress count;
- cancel;
- per-row updates as results arrive;
- final completion event;
- sort only when requested and after completion;
- preserve selection/scroll when reasonable.

## Metadata

Prefer structured server metadata from subscription/control plane.

Fallback to conservative remark parsing.

Never infer a city/country from arbitrary hostname fragments without evidence.

For HotFox-owned servers, a future control plane may provide:
- stable ID;
- city/country;
- region;
- supported transports;
- maintenance state;
- min app version;
- optional fresh capacity.

## Reconnect/backoff policy

Define explicit categories:
- transient network loss;
- server unreachable;
- credentials/config invalid;
- datapath failure;
- DNS failure;
- entitlement expired.

Transient failures may retry.

Permanent/config/auth failures should stop rather than loop forever.

Manual Disconnect always cancels auto-reconnect.

Reset backoff after a stable connected period.

## Diagnostics

For AUTO include a concise reason such as:
- `selected: 31 ms fresh, 0 recent failures`;
- `failover: previous unreachable`;
- `candidate ignored: stale probe`.

This belongs in diagnostics, not the main hero UI.

## Tests

At minimum:
- no measured servers;
- one healthy;
- clear winner;
- tiny latency difference under hysteresis;
- stale fast result vs fresh slightly slower result;
- current healthy handover;
- current dead handover;
- repeated failures;
- recovery;
- timeout;
- cancellation;
- 100+ servers bounded concurrency;
- network loss mid-probe;
- background/battery saver;
- manual selection immune to AUTO;
- switch back to AUTO;
- resolved server removed on refresh;
- all unhealthy -> actionable failure;
- failover attempt cap.

## Exit gate

AUTO should survive a dead server and ordinary network handover without user intervention, without flapping, without overwriting manual mode, and without displaying invented telemetry.
