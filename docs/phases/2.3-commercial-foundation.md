# Phase 2.3 — Commercial Foundation

## Objective

Let a new user obtain HotFox-managed VPN access from the Subscription screen without manually pasting a subscription URL, while preserving external/manual subscription support.

Do not begin this phase until 2.2 exit criteria are met.

## Access origins

HotFox supports two first-class origins:

### A. HotFox-managed access
Purchased through HotFox UI and verified by a trusted backend entitlement.

### B. External/manual access
User imports an HTTPS subscription or compatible individual configuration.

The manual path must remain available even if the HotFox commercial backend is down.

## No-subscription UX

When no access is configured, the Subscription screen should not show an empty URL/status table. Show a commercial onboarding state:

- `HotFox Premium`;
- concise benefits;
- 1/3/12 month plans or backend-configured equivalent;
- exact price/currency;
- recommended badge only if backend supplies it;
- primary `Купить` action;
- secondary `У меня уже есть подписка`;
- optional `Ввести промокод`;
- `Восстановить доступ`;
- privacy/terms links;
- clear note that secure provider checkout opens externally.

## Subscription UI states

Design explicit presentation states:

- NO_ACCESS;
- EXTERNAL_ACTIVE;
- HOTFOX_ACTIVE;
- EXPIRING_SOON;
- EXPIRED;
- PAYMENT_PENDING;
- PAYMENT_FAILED/CANCELLED;
- ENTITLEMENT_PROVISIONING;
- ENTITLEMENT_ACTIVE_SYNC_FAILED;
- BACKEND_UNAVAILABLE;
- RESTORE_REQUIRED.

Do not reuse `Статус неизвестен` for every failure class.

## Plan catalog

Authoritative plans come from backend.

Suggested model:
- id;
- displayName;
- subtitle;
- duration/period;
- priceMinor;
- currency;
- optional oldPrice;
- badge;
- features;
- maxDevices if truly enforced;
- isRecommended;
- availability;
- sortOrder;
- renewalType;
- effective dates/version.

The APK may cache presentation data but must not invent authoritative prices or allow arbitrary client-supplied price checkout.

## Payment architecture

Preferred flow:

`App -> HotFox backend -> payment provider hosted checkout -> provider webhook -> HotFox backend entitlement -> app entitlement fetch -> secure subscription manifest -> server sync -> AUTO -> Connect`

Android should open provider-hosted checkout in Custom Tabs / verified app link flow.

Never:
- put provider private API secrets in APK;
- handle raw card data inside HotFox;
- trust `success=true` in a browser return;
- grant/extend entitlement solely from client polling;
- place bearer entitlement/subscription tokens in redirect URIs.

## Order state machine

Backend order states should be explicit and idempotent, e.g.:

- CREATE_REQUESTED;
- CREATED;
- CHECKOUT_OPEN;
- PENDING;
- PAID;
- ENTITLEMENT_PROVISIONING;
- FULFILLED;
- CANCELLED;
- FAILED;
- EXPIRED;
- REFUND_PENDING;
- REFUNDED.

Invariants:
- immutable order ID;
- create endpoint supports idempotency key;
- provider payment/event ID uniqueness;
- webhook replay safe;
- fulfillment cannot extend entitlement twice;
- client polling is read-only regarding payment truth;
- refund/reversal policy is explicit;
- server-side UTC time.

## Entitlement model

Commercial entitlement is authorization, not raw VLESS configuration.

Possible fields:
- entitlementId;
- customerId;
- source;
- planId;
- startsAt;
- expiresAt;
- status;
- maxDevices optional;
- credentialVersion;
- orderId;
- graceUntil;
- revocationReason.

The backend issues/rotates the actual subscription/bootstrap credential only after validating entitlement.

## Secure provisioning

Preferred model:
- app holds an opaque renewable HotFox client/entitlement credential;
- app calls HotFox backend for a signed/authenticated subscription manifest;
- production private URLs/tokens are not exposed as ordinary UI fields;
- credentials can be rotated/revoked.

If compatibility requires a conventional subscription URL:
- make it per-user opaque;
- support rotation/revocation;
- mask in UI;
- never log;
- store encrypted.

## Android SecretStore

Add a Keystore-backed secret abstraction for:
- entitlement refresh/client credential;
- HotFox-issued subscription token;
- account refresh token if accounts exist;
- restore secret if used.

MMKV may continue to hold non-sensitive metadata/preferences.

Handle:
- keystore invalidation;
- corrupt ciphertext;
- reinstall/restore;
- migration from legacy plain storage if necessary;
- graceful re-auth/restore rather than crash.

## Purchase restore

Commercial launch requires a recovery path after reinstall/device replacement.

Choose at least one robust model:
- optional account + magic link;
- recovery code;
- provider transaction + server verification;
- support-assisted restore with backend evidence.

Never use IMEI/serial/ad ID as irreversible identity.

Generate an opaque install ID rather than hardware fingerprinting.

## Promo/redeem codes

If enabled, backend validates:
- active dates;
- use limits;
- compatible plan;
- per-user/device policy;
- abuse/rate limits.

App displays the server-confirmed final price before checkout.

## Renewal

Manual renewal:
- create new order;
- after verified payment extend from `max(now, currentExpiry)`.

If actual provider recurring billing is later supported:
- backend owns recurring state;
- app shows next billing date/cancel behavior truthfully;
- do not call a reminder-based manual flow `автопродление`.

## Transactional subscription refresh

Both external and HotFox-managed subscription refresh should:

1. fetch into temporary result;
2. parse/validate;
3. reject catastrophic empty/malformed replacement;
4. preserve last-known-good inventory when safe;
5. preserve favorites;
6. preserve manual selection if logically present;
7. preserve AUTO mode;
8. atomically swap only after validation;
9. track last attempt/success/error;
10. explain stale/failed state in UI.

Optional ETag/Last-Modified support may be added if it improves efficiency safely.

## Backend minimum API contract

Suggested endpoints:

- `GET /v1/plans`;
- `POST /v1/orders`;
- `GET /v1/orders/{id}`;
- `GET /v1/entitlement`;
- `POST /v1/entitlement/restore`;
- `GET /v1/subscription/manifest`;
- optional `POST /v1/promo/validate`;
- optional device revoke endpoint if device limits exist.

Use HTTPS, schema validation, request IDs, auth/authorization, rate limits and sanitized structured logs.

## Payment/backend tests

At minimum:
- duplicate order/idempotency key;
- duplicate/out-of-order webhook;
- invalid webhook signature;
- fake success deep link;
- user cancels checkout;
- app killed during checkout;
- payment succeeds while app offline;
- backend crashes during fulfillment;
- entitlement provisioning retry;
- restore after reinstall;
- price changes after catalog fetch;
- promo expiry/double-use;
- refund/reversal;
- keystore invalidation;
- billing backend down while external subscription remains usable.

## Exit gate

Phase 2.3 is complete when a sandbox/test payment can prove:

`choose plan -> create order -> hosted checkout -> backend verifies payment -> entitlement issued -> credentials stored safely -> subscription/server sync -> AUTO remains selected -> real VPN connection works`

without manually pasting a paid HotFox subscription URL and without embedding provider secrets in the APK.
