# Phase 3.0 — Mature HotFox

## Objective

After VPN correctness, commercial access, smart connection, privacy controls and operations are already stable, remove remaining inherited-product friction and mature the architecture.

This is not a justification for a premature rewrite.

## Dedicated VPN engine process

Consider moving the networking engine/service into a dedicated Android process if it materially improves:
- process-wide underlying-network binding isolation;
- lifecycle ownership;
- crash containment;
- UI/control-plane networking separation.

Before migration:
- document current process binding behavior;
- measure actual problems;
- design IPC/state recovery;
- test service/process death;
- preserve notification/VpnService requirements;
- prove no regression in TUN/Xray/HEV path.

Do not split processes purely because it looks architecturally cleaner.

## Control plane / server directory

For HotFox-owned access, mature the backend server directory with trusted metadata:
- stable server ID;
- city/country/region;
- supported transports/features;
- maintenance state;
- optional real capacity;
- health metadata;
- minimum app version;
- rollout groups.

Time-sensitive metadata must have freshness/version rules.

If signed manifests are used, use established signature algorithms/libraries and real key rotation strategy; do not invent cryptography.

## Account/device sync

Optional if product demand requires multi-device restore/management.

Potential capabilities:
- accountless first purchase remains possible if desired;
- optional email/magic-link identity;
- device list/revoke;
- plan/device limit visibility;
- routing/settings sync only where privacy-safe;
- account deletion/export;
- token/session revocation.

Never use invasive hardware fingerprinting as identity.

## Multi-subscription/source management

Power-user capability:
- multiple external/HotFox sources;
- explicit active source/filter;
- stable source IDs;
- source-specific refresh state;
- source-aware AUTO candidate scope;
- duplicate logical server handling;
- safe source deletion while connected.

Keep this out of the ordinary single-subscription user journey unless needed.

## Legacy v2rayNG cleanup

Once coverage exists, remove inherited surfaces that HotFox no longer uses:
- dead drawer/navigation code;
- duplicate hidden navigation widgets;
- unused menu items;
- hidden placeholder views;
- stale naming/resources;
- large Activity methods that now have real domain/repository owners.

Do this incrementally with tests.

Do not remove advanced protocol/import capabilities still used by HotFox.

## Architecture boundaries

Possible mature conceptual layers:

### Presentation
- immutable UI states;
- ViewModels/presentation mappers;
- screens.

### Domain
- Connect/Disconnect;
- SelectServer/AUTO;
- RefreshSubscription;
- Purchase/Restore;
- Routing;
- Diagnostics.

### Repositories/control
- ServerRepository;
- ServerHealthRepository;
- SubscriptionRepository;
- EntitlementRepository;
- BillingRepository;
- RoutingRepository;
- DiagnosticsRepository.

### Engine
- VpnSessionCoordinator;
- VpnEngineFacade;
- XrayRuntime;
- TunBackend;
- DnsController;
- NetworkMonitor;
- PathVerifier.

### Storage/remote
- MMKV ordinary settings;
- Keystore SecretStore;
- richer database only if justified;
- HotFox backend clients.

Avoid empty abstractions that just forward every call.

## Performance/battery hardening

After correctness, profile:
- cold/warm start;
- 100/1000 server list behavior;
- large subscription parsing;
- health probe scheduling;
- memory/FD/thread stability;
- route animation cost;
- 60–120 minute VPN sessions;
- 50-cycle connect/disconnect engineering stress;
- network handover stress;
- Doze/background behavior.

Use measurements before optimization.

## R8/minification

Do not enable minification as an aesthetic milestone.

If introduced:
- separate PR;
- release-only;
- keep rules for native/core/reflection libraries;
- mapping/symbol handling;
- compare APK/runtime behavior;
- physical VPN acceptance again.

## Advanced product backlog

Only after core product quality is high, consider:
- home-screen widget;
- scheduled/trusted-network profiles;
- encrypted config backup;
- family/device plans;
- gift/referral codes;
- Android TV;
- richer foldable/tablet layouts;
- enterprise managed configuration/MDM;
- routing profiles;
- split DNS;
- transport fallback when explicitly supported by backend/core semantics.

## Features to continue avoiding without strong evidence

- decorative fake world map as primary experience;
- fake speed/load/threat counters;
- `AI` branding for deterministic selection;
- crypto/social unrelated features;
- invasive analytics/ad SDKs;
- arbitrary transport mutation to make broken configs connect;
- security claims that cannot be measured.

## Exit vision

HotFox 3.x should feel like an independent product even though it may continue to use excellent upstream VPN/Xray components internally.

A normal user should see a simple privacy app. Complexity should live in a well-tested engine/control plane, not in the user's face.
